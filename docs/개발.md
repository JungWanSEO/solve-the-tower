폴더 구조, 스마트폰 화면 맞춤, 불러오기와 오프라인, 검사 도구, 브랜치 규칙과 배포 순서입니다. 코드를 고치는 사람이 봅니다.

## 9. 스마트폰 화면 맞춤

스마트폰은 화면 크기가 제각각이고, 브라우저의 주소 줄 때문에 실제로 보이는 높이는 더 작습니다. (아이폰 15 는 844 가 아니라 사파리에서 약 664) 그래서 **고정된 크기로 만들지 않고, 보이는 높이를 재서 맞춥니다.**

| 상황 | 처리 | 있는 곳 |
| --- | --- | --- |
| 문제를 풀 때 답 버튼이 화면 아래로 밀림 | 위쪽 줄을 줄이고, 싸우는 그림(132px 까지) → 여백 → 문제 그림 → 글자 → 싸우는 그림(60px 까지) 순서로 모자란 만큼만 줄임. 화면에 여유가 있으면 싸우는 그림은 줄이지 않음 | `js/fit.js` |
| 주소 줄이 접히고 펴짐, 화면 회전 | 그때마다 다시 맞춤 | `js/fit.js` 의 `watchFit` |
| 폭이 좁은 폰 (350 이하) | 여백과 지도 칸을 줄임 | `css/style.css` |
| 보기가 긴 문제 | 답 버튼을 한 줄에 하나씩 | `js/qview.js` |
| 노치, 홈 표시줄 | 안전 영역만큼 여백 | `env(safe-area-inset-*)` |
| 폰을 가로로 눕힘 | "세로로 돌려 주세요" 안내 | `.rotate` |
| 태블릿, PC | 폰 모양의 세로 칸을 가운데에 | `#app { max-width: 480px }` |
| 범위 목록이 김 | 출발 버튼을 화면 아래에 고정 | `.scope-foot` |
| 홈 화면에 추가 | 아이콘과 전체 화면 실행 | `manifest.webmanifest`, `icons/` |

확인한 크기 (한국어·일본어, 문제 유형 7가지씩): 아이폰 SE(375×553), 13 mini, 15, 16 Pro, Pro Max, 갤럭시 S(360×680), 갤럭시 A, 폴드 커버(344), 아이패드. 모두 답 버튼이 스크롤 없이 보입니다. 2016년 아이폰 SE 1세대(320×454)만 일부 문제에서 조금 스크롤해야 합니다.

누르는 곳은 모두 높이 44 이상입니다. 새 화면을 만들 때도 이 기준을 지킵니다.

**넓은 화면 (0.4.0부터).** 폭이 820px 이상이고 가로로 놓인 화면(태블릿, PC)에서는 전투 화면이 두 칸이 됩니다. 왼쪽이 싸우는 그림, 오른쪽이 문제와 답입니다. 규칙은 `css/style.css` 맨 아래의 "넓은 화면의 전투"에 있고, 이때는 `js/fit.js` 가 싸우는 그림을 줄이지 않습니다. 지도·상점 같은 다른 화면은 아직 한 줄 배치(최대 480px)입니다.

**싸우는 그림은 사라지지 않습니다 (0.4.0부터).** 줄이는 순서는 ① 싸우는 그림을 180px까지 ② 여백 ③ 문제 그림을 150px까지 ④ 싸우는 그림을 132px까지 ⑤ 문제 그림을 104px까지, 글자 ⑤ 연속기의 "이미 푼 물음" 접기 ⑥ 싸우는 그림을 최소 96px까지입니다. 그래도 넘치면 그림은 남기고 화면을 내려서 답을 고르게 합니다. (예전에는 답 버튼을 보이게 하려고 그림을 접었는데, 연속기에서 그림이 통째로 사라지는 문제가 있었습니다)

## 9-1. 불러오기 속도와 오프라인

전체 용량은 약 360KB(압축하면 100KB 안팎)로 작습니다. 느리게 느껴졌던 이유는 용량이 아니라 **파일을 하나씩 차례로 기다렸기 때문**입니다. 지금은 이렇게 합니다.

| 한 일 | 있는 곳 |
| --- | --- |
| 코드 파일 20여 개를 한꺼번에 받기 | `index.html` 의 `modulepreload` |
| 글·문제·몬스터 데이터를 한꺼번에 받기 | `js/main.js` 의 `boot`, `js/questions.js` 의 `loadAll` |
| 받는 동안 진행 막대, 6초가 넘으면 "통신이 느립니다", 실패하면 이유와 "다시 시도" | `index.html` 의 `#loading` |
| 한 번 열면 기기에 저장 → 다음부터는 통신 없이 바로 열림, 오프라인에서도 실행 | `sw.js` |
| 새 버전이 올라오면 "새 버전이 준비됐습니다 · 새로 고침" 알림 | `sw.js`, `js/main.js` 의 `watchUpdate` |
| 전투 화면이 아닐 때는 캐릭터 그림판을 쉬게 함 | `js/stage.js` 의 `loop` |

**단계별 풀이 쓰는 법**

풀이(`explain`)에 줄바꿈(`\n`)을 넣으면 줄마다 한 단계가 되어 ①②③ 번호가 붙어 나옵니다. 줄바꿈이 없으면 지금까지처럼 한 줄로 나옵니다.

- 한 문제에 3~4단계가 적당합니다. 마지막 단계에는 `{answer}` 를 넣습니다. (알림 줄처럼 좁은 곳에는 마지막 단계만 나옵니다)
- 중간 계산을 실제 숫자로 보여 주려면 생성기(`js/generators.js`)가 그 값을 함께 돌려주게 하고 `{이름}` 으로 씁니다. 예: 이차방정식의 `{fac}`(인수분해한 식), `{prod}`·`{lin}`(곱과 합), 최대·최소의 `{vs}`·`{vt}`(양 끝의 값).
- 숫자를 넣기 어려운 문제는 "무엇을 어떤 순서로 하는지"를 단계로 적습니다.
- **계산식 `{= 식 }`**: 풀이 글 안에 `{= b*b + c*c - 2*b*c*cosd(A) }` 처럼 적으면 그 문제의 숫자로 계산한 값이 들어갑니다. 생성기를 고치지 않고도 중간 결과를 보여 줄 수 있습니다. 식에는 생성기가 돌려준 값의 이름과 `js/calc.js` 의 도구(`nPr`, `nCr`, `fact`, `gcd`, `lcm`, `pf`(소인수분해), `seq`(곱으로 풀어 쓰기), `ev`(식에 x 넣기), `Fint`(적분한 식의 값), `cosd`, `sind`, `sqrt`, `round`, `floor`, `max`, `min`)를 쓸 수 있습니다. 정수가 아니면 분수로, 제곱해서 분수가 되는 수는 루트(`√3/2`, `2√6`)로 나옵니다. 문제에 보이는 글에서 숫자를 읽어 내는 도구도 있습니다: `nums`(글 속의 수), `lin`·`co`(식의 계수), `fac`(인수분해), `pair`(합과 곱으로 두 수 찾기), `qroots`·`iroots`(근), `cx`(복소수), `lineco`(직선의 계수), `circ`(원의 중심과 r²), `exps`(지수), `euclidS`(호제법 과정), `divs`·`expand10`(n진법), `sqpart`(제곱수 부분).
- 풀이 280개(문제 틀 211개, 연속기 물음 69개)는 모두 단계별입니다. `npm run verify` 의 `verify-explain` 이 풀이를 실제 숫자로 채워 보고, 빈 자리표시나 계산되지 않은 식이 있으면 알려 줍니다.

**풀이는 맞혀도 나옵니다**

답을 고르면 맞혔든 틀렸든 답 바로 아래에 정답과 풀이 카드가 뜨고, "다음"을 눌러야 넘어갑니다. 찍어서 맞힌 문제도 풀이를 보며 복습하게 하려는 것입니다. 맞힌 카드는 노란색("정답! …"), 틀린 카드는 청록색("정답: …")입니다. 연속기는 물음마다 카드가 나옵니다. 맞힌 문제의 멈춤은 `js/battle.js` 의 `reviewThen` 이 맡습니다. (문제마다 한 번, 공격 연출이 끝난 뒤에 멈춥니다)

**탑은 항상 3막**

범위를 고르고 시작하면, 고른 유형을 배우는 순서대로 셋으로 나눠 3막(막마다 10층, 모두 30층)을 차례로 오릅니다. 예전의 "짧은 탑"은 0.5.0 에서 없앴습니다.

| 항목 | 내용 |
| --- | --- |
| 나누는 법 | 단원의 경계에서, 세 막의 유형 수가 비슷해지게 (`js/questions.js` 의 `actsFor`) |
| 유형이 5개 이하일 때 | 나누지 않고, 세 막 모두 고른 범위 전체에서 냄 |
| 몬스터·보스 | 그 막의 단원 것 |
| 끝 | 막의 보스를 이기면 다음 막, 마지막 막의 보스를 이기면 클리어 |
| 튜토리얼 판 | 지도 한 장(10층)으로 끝남 |

- 막을 넘어갈 때 체력을 12 회복하고 새 지도를 받습니다. 골드, 강화, 힌트, 최대 체력은 그대로 이어집니다.
- 뒤의 막일수록 적의 체력이 10%씩 늘어납니다. 숫자는 `js/config.js` 의 `act` 에 있습니다.
- 진행 중인 판은 `run.acts`(막의 목록), `run.act`(지금 막), `run.full`(고른 전체 유형)에 저장됩니다. `run.scope` 는 지금 막의 유형입니다. `run.acts` 가 없는 판(튜토리얼, 예전의 짧은 탑)은 지도 한 장으로 끝납니다.

**일본어 문장 검수 (표 파일로 주고받기)**

게임을 하면서 문장을 하나씩 확인하기는 어려우므로, 일본어 문장을 모두 표 파일로 뽑아서 검수받고 다시 넣습니다.

1. `node tools/script-export.mjs` — 화면 글, 단원·유형 이름, 문제문, 풀이, 연속기, 몬스터의 일본어를 모두 모아 `script/ja-script.json` 을 만듭니다. (꺼 둔 단원은 빠집니다)
2. `python3 tools/script-xlsx.py make` — `script/ja-script.xlsx` 를 만듭니다. 이 파일을 검수하는 분께 보냅니다. 첫 탭에 일본어로 쓴 안내가 있습니다.
3. 검수하는 분은 고칠 줄만 노란 칸("直した日本語")에 적습니다. `{a}` 같은 자리표시는 그대로 둡니다. "表示の例" 칸에서 숫자가 들어간 실제 모습을 볼 수 있습니다.
4. 돌려받은 파일로 `python3 tools/script-xlsx.py read <파일>` — 고친 줄만 `script/ja-fixes.json` 으로 뽑습니다. 메모만 적힌 줄은 화면에 따로 보여 줍니다.
5. `node tools/script-import.mjs script/ja-fixes.json` 으로 바뀔 곳을 미리 보고, 괜찮으면 끝에 `--write` 를 붙여 게임 파일에 넣습니다. 자리표시가 원문과 다른 줄은 넣지 않고 알려 줍니다.
6. `npm run verify` 를 돌리고 `sw.js` 의 `VERSION` 을 올립니다.

표의 "前回から" 칸에는 지난 검수 뒤에 **새로 생긴 줄(新規)** 과 **일본어가 바뀐 줄(変更)** 이 표시됩니다. 비교 기준은 `script/ja-script.base.json` 입니다. 검수를 한 번 마치고 고친 내용을 다 넣었으면, 그때의 `script/ja-script.json` 을 `script/ja-script.base.json` 으로 덮어써서 기준을 새로 잡습니다.

문제를 더 만든 뒤에는 1~2번을 다시 하면 새 표가 나옵니다. 이미 고친 문장은 게임 파일에 들어가 있으므로 새 표의 "日本語(いま)" 에 고친 문장이 나옵니다.

**고쳐서 올릴 때 꼭 할 일: `sw.js` 의 `VERSION` 을 바꿉니다.** 바꾸지 않으면 이미 열어 본 사람에게는 예전 화면이 계속 나옵니다. 처음 화면 맨 아래에 지금 버전이 작게 적혀 있어서, 새 버전이 적용됐는지 바로 확인할 수 있습니다. 파일을 새로 만들었으면 `sw.js` 의 `FILES` 와 `index.html` 의 `modulepreload` 에도 추가합니다.

게임 안에서 화면이 넘어갈 때는 통신을 하지 않습니다. 느린 폰을 흉내 낸 측정에서도 가장 긴 전환(처음 화면 → 범위 고르기)이 0.3초 이내였습니다.

## 9-2. 고친 뒤 확인하기 (검사 도구)

`tools/` 폴더에 검사 도구가 있습니다. 게임은 이 폴더 없이 동작합니다.

| 명령 (`tools/` 에서) | 확인하는 것 |
| --- | --- |
| `npm run verify` | 모든 문제의 정답을 다른 방법으로 다시 계산해 대조. 검사가 안 붙은 문제 틀도 찾아냄 |
| `npm run balance` | 정답률이 다른 봇들이 여러 판을 해서 클리어율과 쓰러진 층을 측정. 게임 숫자를 고쳤을 때 사용 |
| `npm run play` | 봇이 게임을 끝까지 여러 판 진행. 오류와 빠진 번역 확인 |
| `npm run layout` | 스마트폰 14가지 크기에서 답 버튼이 화면 밖으로 밀리는지 측정 |
| `npm run perf` | 느린 통신에서 첫 화면이 뜨는 시간 측정 |

준비와 결과 읽는 법은 `tools/README.md` 에 있습니다. **문제를 새로 만들면 검사도 같이 만듭니다.** 안 만들면 `verify` 마지막 줄에 `NOT VERIFIED` 로 나옵니다.

## 9-2-1. 업데이트 소식 쓰는 법

게임 안의 "업데이트 소식" 창은 `data/news.json` 을 그대로 보여 줍니다. 개발 기록인 `CHANGELOG.md` 와는 따로이고, **학생이 읽는 글**입니다.

1. 배포할 때 `data/news.json` 의 맨 위에 새 버전을 하나 더합니다. (맨 위가 가장 새 버전)
2. `version` 은 버전 번호, `date` 는 낸 날짜(아직 내지 않았으면 빈 글), `items` 는 언어마다 3~5줄입니다.
3. 한 줄은 "무엇이 생겼는지"를 학생의 말로 짧게 씁니다. 파일 이름이나 숫자 조정 같은 개발 이야기는 넣지 않습니다.
4. 맨 위 버전이 바뀌면, 그 버전을 처음 여는 사람에게 창이 한 번 저절로 뜹니다. (튜토리얼을 아직 안 끝낸 사람에게는 뜨지 않습니다)

소식의 일본어도 검수 스크립트(`script/ja-script.xlsx`)의 "画面の文" 탭에 들어갑니다 (키는 `news:<버전>:<줄 번호>`).

## 9-3. 브랜치 규칙 (git-flow)

| 브랜치 | 쓰임 |
| --- | --- |
| `main` | 배포용. 정식 공개 뒤 GitHub Pages 가 이 브랜치를 보여줍니다. 직접 커밋하지 않습니다. |
| `dev` | 개발용. 완성된 기능이 모이는 곳입니다. |
| `feature/<이름>` | 기능 하나를 만드는 곳. `dev` 에서 만들고 `dev` 로 합칩니다. |
| `release/<버전>` | 배포 준비. `dev` 에서 만들고 `main` 과 `dev` 양쪽에 합칩니다. |
| `hotfix/<이름>` | 배포된 것의 급한 수정. `main` 에서 만들고 `main` 과 `dev` 양쪽에 합칩니다. |

**기능 하나를 만드는 순서**

```
git switch dev
git switch -c feature/offline
(작업하고 커밋)
git switch dev
git merge --no-ff feature/offline
```

**배포하는 순서**

```
git switch -c release/0.1.0 dev
(버전 확인, 마지막 수정, CHANGELOG.md 의 "다음 버전" 을 버전 번호로 바꾸기)
git switch main
git merge --no-ff release/0.1.0
git tag v0.1.0
git switch dev
git merge --no-ff release/0.1.0
```
